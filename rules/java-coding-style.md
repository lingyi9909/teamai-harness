# Java Coding Style

遵循项目已有风格；以下规则只在项目没有更具体约束时作为默认值。

## 设计原则

- 优先清晰、可维护和可测试，而不是技巧性写法；
- 保持高内聚、低耦合，优先按业务能力/领域组织代码；
- 抽象必须由真实重复或稳定边界驱动，避免为了“以后可能用”提前设计框架；
- 小改动优先复用现有模式，不引入第二套并行架构；
- 对跨层共享的协议、DTO、事件和枚举，显式考虑兼容性。

## Java 语言使用

- 使用项目已经支持的 Java 版本特性，不越过当前 toolchain/source level；
- 对不可变值优先使用 `final`、record、不可变集合或不可变对象，但不为形式上的不可变制造大量无价值复制；
- `Optional` 主要用于返回值表达“可能不存在”，不要机械用于字段、参数或集合元素；
- collection 返回空集合优于返回 `null`，除非现有 API 契约明确区分二者；
- `equals`/`hashCode`/`compareTo` 必须满足对应契约；
- 金额使用项目既定的精确表示，常见为 `BigDecimal` + 明确 rounding/scale，不使用浮点数承担精确货币计算；
- 时间优先使用 `java.time` 并明确时区/offset 语义，不用系统默认时区掩盖业务语义；
- 并发代码必须说明共享状态、可见性、原子性和线程池 ownership。

## 方法与类

- 一个方法聚焦一个清晰目的；复杂逻辑通过有业务含义的私有方法或领域对象拆分；
- 避免过深嵌套，优先 guard clause；
- 不用布尔参数隐藏两套完全不同的流程，必要时拆成有语义的方法或策略；
- 不把所有逻辑塞进 Controller，也不创建只做无意义转发的“层”；
- 新增 abstraction 时必须能指出至少一个真实变化点或隔离边界。

## 异常

- 不吞异常；
- 不使用 `catch (Exception)` 作为默认控制流；只有明确的边界层、补偿/降级或最终错误映射才允许广泛捕获；
- 保留原始 cause；
- 业务异常与系统异常的边界遵循项目现有约定；
- 不在异常消息、日志或 API response 中泄露 secret、token、完整敏感请求体或数据库凭据。

## 日志

- 使用项目已有日志框架和结构化字段习惯；
- 不使用 `System.out/err` 代替服务日志；
- 错误日志要包含定位所需上下文，但避免重复在多层记录同一异常堆栈；
- 用户标识、订单号等可能敏感字段按项目脱敏规范处理；
- 高频路径避免无意义 INFO 日志和大对象序列化。

## Lombok / MapStruct / 代码生成

只有项目已经采用对应工具时才继续使用；不要为一个小需求新引入 Lombok、MapStruct 或新的 annotation processor。

## 格式化

遵循项目已有 formatter/checkstyle。不要在业务修改中格式化无关文件或制造大面积 whitespace diff。
